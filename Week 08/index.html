MIDTERM DOCUMENTATION

PCom Assistant

I made this web tool to help product designers start a simple physical-computing prototype. It suggests an electronic approach, a short parts list, and a first test.

User
Charlie, product designer
Focus
Early functional prototyping
Current state
Local AI prototype

01 / THE PROBLEM

Project idea

Charlie can communicate a product idea through sketches and 3D models. The frustrating point comes when the object needs to do something: light up, move air, respond to a button, or run from a battery.

I decided not to make a tool that designs the entire product for him. The narrower goal is to help with the first electronics decisions:

  • Does this idea need a microcontroller at all?
  • What are the fewest parts needed for the main function?
  • Will the parts fit in the available space?
  • What should be connected and tested first?
“Be simple” became the main rule. A light with one button should not become an ESP32 project unless programmable behavior is actually needed.

02 / PROCESS

How I developed it

A

Interface sketch

The first drawing established a project library, a conversation area, and a structured plan on one page. I removed image generation and internal product-layout advice to keep the scope realistic.

B

Draft 1

The first coded version used sample data. It helped me test the hierarchy of the plan before connecting an API: solution, parts, wiring, dimensions, and first test.

C

AI conversation

With help from Codex, the next version connected the DeepSeek API. The API key stays outside the browser. The assistant asks one question at a time, then returns a structured plan.

DEEPSEEK IN THE TOOL

Conversation and Plan generation

  • Asks the user for missing project constraints.
  • Suggests the simplest functional circuit it can find.

  • Does not design the page or decide the project scope.

My role remained central: I set the scope, chose which features to keep, tested the answers, identified unsafe or overcomplicated suggestions, and decided how the tool should change.

Codex also helped me organize and edit this process documentation based on my project notes, decisions, and testing results.

04 / CURRENT OUTPUT

What the tool does

The current tool keeps the conversation and the plan side by side. A generated plan can include:

  1. 01 Simplest solution
  2. 02 Shopping list with reference sizes
  3. 03 Simple functional flow
  4. 04 Basic low-voltage wiring
  5. 05 First test steps
  6. 06 Optional ESP32-C3 upgrade

The ESP32 section is only generated when the requested behavior needs sensing, wireless control, timing, or programming.

05 / USER TESTING

User testing

WHAT I EXPECTED

A familiar AI conversation

I expected people to interact with the tool in a way similar to Codex: create a project, describe a product idea in the chat, answer a few questions, and receive a prototype plan.

WHAT HAPPENED

The first action was unclear

Most people were not sure what to do first when they opened the page. Charlie experienced the same problem. I think too many visual elements compete for attention, while the main starting action is not clear enough.

WHAT I WOULD CHANGE

Reduce friction at the beginning

I would simplify the interface, add a short onboarding message, and show example prompts near the input. Several testers also requested images or diagrams because text-only plans can feel too abstract. Image recognition and generation were outside the technical scope of this version, but simple component diagrams could be explored later.

06 / PROTOTYPE TESTING

Earlier prototype tests

TestWhat happenedChange
Small fan

The assistant correctly recognized that a basic fan did not need a microcontroller, but it still needed clearer power and size information.

Ask only for missing constraints and keep the controller optional.

One-button flashlight

The first answer proposed two AAA cells plus a boost module. A second pass found a simpler three-cell circuit, but the suggested LED current was too high.

Add a simplicity audit, conservative LED-current rules, and a required resistor calculation.

Wearable safety light

The assistant repeated questions that had already been answered, and early language switching translated only part of the page.

Preserve conversation context and translate the full interface, messages, project names, and plan.

07 / ITERATION

Changes I made

  • Shorter answers. The assistant now gives a compact plan instead of a long essay.
  • Safety limits. Low-voltage guidance only; no mains wiring; conservative current assumptions.
  • Fewer components. Normally no more than six main parts, unless every extra part is necessary.
  • Size honesty. Unknown dimensions are marked “Confirm seller dimensions” instead of being invented.
  • Project memory. Plans can be saved locally, renamed, pinned, and deleted.
  • Full-page language switching. English is the default, with Chinese available for the entire page.
  • Usable layout. Chat and Plan scroll independently, so the message field stays visible at normal desktop sizes.

These are selected excerpts from my work with Codex. The original conversation was in Chinese, so the excerpts below are translated into English. I made the project decisions, tested the application, and reported problems. Codex assisted with interface planning and technical debugging.

EXCERPT 01 · INTERFACE PLANNING

Defining the page before coding

Me

“The tool cannot make simple things more complicated. If an LED ring, a button, and a battery can do the job, it should not add a controller. Be simple.”

Codex

“Next, define the page structure before writing code. I suggest a single-page tool: requirements on the left, generated results on the right, followed by the complete plan. The page should clearly state that it recommends the simplest functional circuit and only uses an ESP32 when necessary.”

EXCERPT 02 · TROUBLESHOOTING

Resolving a local server conflict

Me

“The server reports EADDRINUSE: address already in use 127.0.0.1:3000.”

Codex

“The server will now search for an available port automatically. If 3000 is occupied, it will try 3001, then continue up to 3009. Open the new address shown in the server window.”

09 / WHAT IS NEXT

Next steps

The tool can already hold a conversation and generate a structured prototype plan, but it is not a replacement for a datasheet or an experienced electronics review.

Next tests

  • Test the tool with Charlie using one of his real product ideas.
  • Compare generated component dimensions with seller listings.
  • Make confirmed requirements visible so questions are not repeated.
  • Test whether the first wiring plan produces a working breadboard prototype.

What I learned

The most useful part of this project is not generating more ideas. It is reducing uncertainty at the moment when a visual concept needs to become physical and functional.
